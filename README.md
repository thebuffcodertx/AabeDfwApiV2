# AabeDfwApi

A backend API for the AABE (American Association of Blacks in Energy) DFW Chapter website — built from scratch to replace their current GoDaddy site. This is both a real client project and a portfolio piece for learning full-stack development.

## What This Project Does

The DFW chapter needs a website that can:

- Let people **sign up** as members
- Show an **events calendar**
- **Accept payments** for events
- Display info about the **organization and its committees**

This repo is the **backend** — it stores the data and exposes it so a frontend (built later in Angular) can display it and let users interact with it.

## The Stack, and Why

| Piece                               | What it is                                  | Why we're using it                                                               |
| ----------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------- |
| **ASP.NET Core Web API**            | A framework for building backend APIs in C# | Industry-standard for .NET backends, in-demand skill                             |
| **Entity Framework Core (EF Core)** | An ORM (Object-Relational Mapper)           | Lets us write C# classes instead of raw SQL to define and query the database     |
| **SQL Server**                      | The actual database                         | Pairs naturally with EF Core; runs locally in Docker for now                     |
| **Docker**                          | Runs SQL Server in an isolated container    | Avoids installing SQL Server directly on the Mac (not natively supported anyway) |
| **Angular**                         | Frontend framework (not started yet)        | Will consume this API and render the actual website                              |

## Key Concepts Explained

**What's an API?**
A way for two programs to talk to each other. Our Angular frontend will send requests (e.g. "give me the list of events") to this backend, and the backend responds with data.

**What's a model?**
A C# class that represents one "thing" in our data — a `Member`, an `Event`, etc. Each property on the class becomes a column in a database table.

**What's a DbContext?**
The bridge between our C# code and the actual database. `AppDbContext` is where we tell EF Core "here are all my tables (DbSets), and here's how they relate to each other."

**What's a migration?**
A snapshot of changes to your data models, translated into the SQL needed to update the actual database. Every time you change a model (add a property, add a new model), you create a new migration and "apply" it to update the real database to match.

**What's a namespace?**
A way of organizing code so C# knows where to find a class. Every model file needs `namespace AabeDfwApi.Models { }` wrapped around it, or other files won't be able to see it — a small thing that causes confusing errors if forgotten.

## Data Model Overview

- **Member** — a person who's part of the chapter
- **Committee** — a sub-group within AABE DFW (e.g. Programs, Membership)
- **Event** — something a Committee hosts; has a price, date, and optional image
- **Signup** — links a Member to an Event they're attending
- **Payment** — tracks whether a Signup has been paid for (Stripe integration planned)

**How they relate:**

- One Committee → many Events (a committee can host multiple events)
- One Event → many Signups (many people can sign up for one event)
- One Member → many Signups (a member can sign up for multiple events)
- One Signup → one Payment (each signup has one payment record)

## Project Structure

```
AabeDfwApi/
├── Controllers/     # API endpoints — one Controller per model, handles GET/POST/PUT/DELETE
├── Models/          # C# classes representing our data (Member, Event, etc.)
├── Data/            # AppDbContext — configures the database
├── Migrations/      # Auto-generated by EF Core — tracks database schema changes over time
├── Properties/      # Launch settings (which port the app runs on locally)
├── Program.cs       # App entry point — where services get registered and the app starts
├── appsettings.json # Configuration, including the database connection string
```

## Local Setup (from scratch)

1. **Confirm tooling is installed:**

   ```
   dotnet --version   # should show 10.x
   docker --version
   docker ps          # confirms Docker Desktop is running
   ```

2. **Create the project:**

   ```
   dotnet new webapi -n AabeDfwApi
   cd AabeDfwApi
   dotnet build
   ```

3. **Add EF Core packages:**

   ```
   dotnet add package Microsoft.EntityFrameworkCore.SqlServer
   dotnet add package Microsoft.EntityFrameworkCore.Design
   ```

4. **Build the Models** (in a `Models/` folder — see Data Model Overview above), each wrapped in `namespace AabeDfwApi.Models { }`.

5. **Build `Data/AppDbContext.cs`** with a `DbSet` for each model and relationship configuration in `OnModelCreating`.

6. **Wire it up in `Program.cs`:**

   ```csharp
   using Microsoft.EntityFrameworkCore;
   using AabeDfwApi.Data;

   builder.Services.AddDbContext<AppDbContext>(options =>
       options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));
   ```

7. **Add the connection string** to `appsettings.json` — do this _before_ running any `dotnet ef` commands, or you'll get a "ConnectionString property has not been initialized" error:

   ```json
   "ConnectionStrings": {
     "DefaultConnection": "Server=localhost,1433;Database=AabeDfwDb;User Id=sa;Password=YourStrong@Passw0rd;TrustServerCertificate=True"
   }
   ```

8. **Start SQL Server and run the first migration:**

   ```
   docker start sql-server
   dotnet ef migrations add InitialCreate
   dotnet ef database update
   ```

9. **Build a Controller for each model** (in a `Controllers/` folder) — each one gets GET (list), GET (by id), POST, PUT, and DELETE endpoints, using `AppDbContext` to talk to the database. Then register controllers in `Program.cs`:

   ```csharp
   builder.Services.AddControllers();   // before builder.Build()
   ...
   app.MapControllers();                 // before app.Run()
   ```

10. **Test each endpoint** in Postman or the browser (GET requests work directly in the browser URL bar) to confirm data can actually be created and retrieved.

11. **Push to GitHub:**
    ```
    git init
    git add .
    git commit -m "Initial commit"
    git remote add origin <your-repo-url>
    git branch -M main
    git push -u origin main
    ```
    Make sure `.gitignore` (VisualStudio template covers .NET) is in place _before_ your first commit, so `bin/`, `obj/`, and secrets never get tracked.

## Decisions Made Along the Way

- **Local dev now, Azure SQL later** — Docker + local SQL Server for development; will migrate the connection string to Azure SQL when ready to deploy.
- **Nullable strings (`string?`)** used throughout models — standard .NET 8+ convention, avoids compiler warnings for properties that might not always have a value.
- **`ImageUrl` on Event** — added for future support of event images (similar to Eventbrite-style cards). Stores a URL/path, not the actual image file.
- **Swapped Swashbuckle for built-in OpenAPI** — Swashbuckle 6.6.2 isn't compatible with .NET 10 and crashed EF Core's migration tooling. `AddOpenApi()` / `MapOpenApi()` are .NET 10's native replacement. No Swagger UI currently — could add `Scalar.AspNetCore` later for browsable docs.
- **Fixed decimal precision warnings** — `Event.Price` and `Payment.Amount` had no explicit SQL column type, risking silent truncation. Added to `OnModelCreating`:

  ```csharp
  modelBuilder.Entity<Event>()
      .Property(eventItem => eventItem.Price)
      .HasPrecision(10, 2);

  modelBuilder.Entity<Payment>()
      .Property(payment => payment.Amount)
      .HasPrecision(10, 2);
  ```

  `HasPrecision(10, 2)` = up to 10 total digits, 2 after the decimal point.

- **Important migration order** — any time you change a model or `OnModelCreating` (like the fix above), you must run `dotnet ef migrations add <SomeName>` _before_ `dotnet ef database update`. Running `database update` without a fresh migration first throws a `PendingModelChangesWarning` error.
